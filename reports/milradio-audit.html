缺陷 01 数据实证

音频帧解析偏移 2 字节，S-meter 记录的其实是帧计数器

kiwi_client.py 把 SND 帧的 body 解析成 flags(1) + seq(2, 大端) + smeter(2) + 音频。 但数据库里的 S-meter 值出卖了真实布局：全部 744 条记录只有 16 个不同取值，而且每一个反推回原始整数都是 256 的整数倍。

证据 A — S-meter 列的全部取值

SELECT DISTINCT s_meter_dbm FROM signals;   → 16 行

反推 raw = (dBm + 160) / 150 × 65535 :
  0   256   512   768   1024  1280  1536  1792
  2048  2560  3584  4864  5632  6656  7424  7680

全部 ≡ 0 (mod 256)   →  低字节恒为 0x00
真实 S-meter 会在 0–4095 连续抖动，绝不会这样。

676 / 744 条记录的 S-meter = 恰好 -160.0 dBm（raw = 0）

这些值是小端 uint32 帧计数器的高位字节：若 body[1:5] 是 seq，则 body[3] = ⌊seq/65536⌋、 body[4] = 0——正好解释了"256 的倍数"和"短会话恒为 0、长会话逐级增大"。

seq 是 4 字节小端而非 2 字节大端，S-meter 在 body[5:7]， 音频从 body[7:] 开始。当前代码从 body[5:] 起取音频， 于是每帧多出 1 个假样本——就是那两个 S-meter 字节被当成了一个 int16。

证据 C — 每段录音里的周期性脉冲

此外 dBm 换算公式本身也不对。raw/65535×150−160 是凭空拟的； KiwiSDR 的实际换算是 0.1 × (raw & 0x0FFF) − 127。 两件事叠加的结果是：S-meter 这一列从来没有记录过任何真实的信号强度， 依赖它的图表、阈值和对比全部落空。

缺陷 02 数据实证

调制识别的结果由字典顺序决定，不由信号决定

_estimate_modulation() 给带宽 2 分、平坦度 1 分、峰均比 1 分。 问题在于带宽这一项测的是接收机的滤波器，不是信号： 客户端把 USB 通带写死成 300–3000 Hz，所以无论对面发的是语音、FSK 还是纯噪声， 量出来的带宽都是同一个数。

证据 — 带宽毫无区分度

判定类型数量平均带宽平均 SNR
USB_VOICE6912759 Hz5.8 dB
NOISE432782 Hz2.5 dB
PSK102784 Hz5.6 dB

三个"不同"的调制类型，平均带宽差 25 Hz（<1%）。全库带宽 min 932 / max 2846 / avg 2760 Hz——一根柱子。

证据 — 用真实数据重跑打分器

对 744 条 analysis 记录重放 _estimate_modulation() 的打分：

  最高分只有 1 个类型独得   10 条
  最高分 2 个类型并列        1 条
  最高分 3 个类型并列        690 条   ← 98.4%

  满分 4 分的            1 条
  只得 3 分的          700 条

并列时 max() 取字典里第一个命中的键。
MODULATION_PROFILES 的第一项恰好是 USB_VOICE。

所以"93% 的信号是 USB 语音"不是一个观测结果， 它只是 MODULATION_PROFILES 的书写顺序。

缺陷 03 高

SNR 把滤波器阻带当成了噪声基准

_estimate_snr() 取峰值两侧 ±10% 频谱当信号、其余当噪声。 但频谱跨度是 0–6000 Hz，而信号只可能存在于 300–3000 Hz—— "噪声区"里塞了一大片 3000–6000 Hz 的滤波器阻带。 那里几乎没有能量，于是分母被压低，SNR 被系统性地扭曲。

症状在分布上很明显：385/744 落在 3–6 dB， 310/744 落在 6–10 dB，只有 6 条超过 10 dB。 一段清晰可辨的 EAM 语音，真实带内 SNR 应当在 20 dB 以上。 现在这个指标既区分不开好坏信号，也没法用来卡阈值。

第二部分

采集策略

7 天 / 32 次会话

过半"信号"其实只是静噪的尾巴

tail_time = 3.0 s，意味着任何一次触发至少产出 3 秒录音。 而时长分布里 424/744（57%）落在 3–5 秒—— 真实信号部分不到 2 秒，比一次台标呼号还短。

反方向也有问题：84 次信号在同频率上距上一条不到 8 秒就开始， 这是同一次通话被切成了多条记录。 一边把噪声记成信号，一边把一次通话记成好几次， 所以"信号数"和"平均时长"两个统计量目前都不能用。

频率库有 20 个频率，实际只用过 2 个

frequencies.yaml 编了 5 个网络共 20 个频率， 数据库里却只有 11175（679 条）和 8992（65 条）。 max_concurrent: 2 这个配置项从来没有被任何代码读过—— 监听始终是单连接、单频率。

这恰好错过了这个领域里最有价值的一个特性： HFGCS 是同播网络，同一条 EAM 会在 4724 / 6712 / 8992 / 11175 / 13200 / 15016 上同时发出。一次只听一个频率，等于主动扔掉了唯一一个可以互相印证的信息源。

会话生命周期泄漏

32 次会话里有 18 次 的 end_time 是 NULL、状态仍是 running。Ctrl+C 与异常退出的路径没有走到 end_session()。 任何按会话时长归一化的指标（每小时信号数、节点在线率）现在都算不出来。 修法很轻：进程退出时把所有 running 会话标记为 interrupted。

第三部分

工程卫生

.git = 180 MB

仓库里没有 .gitignore，于是 764 个 WAV、SQLite 数据库本体、 20 个 .pyc 全部进了版本库。代码本身只有 9,336 行， .git 却已经 180 MB，而且这个数字只会随着监听时长单调增长。

另外根目录还躺着一个 0 字节的文件 =（一次重定向手误）， 以及 8 个一次性排查脚本（check_*.py、diagnose_*.py、 inspect_frames.py、example_*.py）。 它们当时都有用，但现在和正式模块混在同一层，新人分不清哪些是系统的一部分。

测试是 18 个全绿，覆盖 squelch / db / analyzer。 唯独没有一个测试碰过 kiwi_client 的帧解析—— 而这正是缺陷 01 藏身的地方。一个喂进构造帧、断言解出的样本数与 S-meter 的单元测试， 当初就能挡住它。

新功能建议

分三层，后层依赖前层
第一层

把地基修成可信的

这三项不是"新功能"，但它们决定了后面所有功能是否有意义。 在坏读数上做告警、做分类、做关联，只会把错误放大。

真实 S-meter → 用 dBm 做静噪门限

半天

修好帧解析后，S-meter 立刻变成一个真实可用的信号强度序列。 这带来一个当前架构拿不到的能力：门限可以用 dBm 表达。

现在的 open_threshold: 0.10 是 RMS 值， 而 RMS 取决于对面节点的 AGC 设置——CHANGELOG 里 0.65 → 0.15 → 0.10 三次手调， 调的其实是"KPH 这个节点的 AGC"。换个节点这个数就又不对了。 dBm 门限是节点无关的，一次设定处处适用。

前置：缺陷 01 · 顺带消除全部录音里的 23.4 Hz 嗡声

自适应噪声基底静噪

1–2 天

把固定门限换成滚动噪声基底 + 固定余量：持续统计近 N 分钟 RMS 的低分位数 （比如 20th percentile）作为基底，开启门限取"基底 + 6 dB"。

它同时解决两个方向的问题——白天电离层条件变化、换节点、换频段时不再需要手调， 并且能自动收紧那 57% 的短触发。这是对反复手调阈值这件事的一次性了结。

直接针对：57% 垃圾录音 + 三次手工调参的历史

通话缝合（transmission stitching）

半天

同频率上间隔小于 N 秒（建议 15 s）的相邻信号，合并成一条逻辑通话， 数据库加一层 transmissions 表，signals 作为其片段。

立刻修正那 84 次被切碎的通话，让"时长分布""每小时通话数"这些统计第一次变得可信。 报告里的图表不用改，换个数据源即可。

第二层

真正的新能力

地基修好后，这几项能让项目从"录音机 + 统计"变成"能回答问题的仪器"。 按价值排序。

多频率并行监听 + 同播交叉验证

3–5 天 · 旗舰

开 N 条并发 KiwiSDR 通道（max_concurrent 终于派上用场）， 同时盯住 HFGCS 同播频率组。然后做一件单频率永远做不到的事： 同一条 EAM 在 8992 和 11175 上 ±2 秒内同时出现 → 判定为真实发射。

这是比任何单通道启发式规则都强的垃圾过滤器——本地噪声、脉冲干扰、 邻频串扰都不可能在两个相隔 2 MHz 的频率上同时出现。它用物理规律代替阈值。

附带产出一张自己测出来的传播表：哪个频率在哪个时段 SNR 最好。 你现在的数据只能说"11175 有 679 条"，不能说"11175 在 13 UTC 比 8992 好 8 dB"。

前置：第一层全部 · 单节点通道数通常允许 4–8 路

EAM 报文结构识别

2–4 天

EAM 有极强的结构特征：呼叫前导、SKYKING SKYKING DO NOT ANSWER、 一串音标字母、然后整段重复一遍。这个"重复"是免费的分类器—— 对包络做自相关，通话内部出现高相关的重复段 → 是格式化报文； 日常空管闲聊不会重复。不需要任何语音识别就能拿到。

再进一步可以接 Whisper 转写那串音标字母。你已经有 fetch_public_logs.py 和 compare_eam.py 在抓 EAM.watch 的 ground truth——一旦能转写，对比就从"时间戳撞上了"升级成"报文内容对上了"。

复用：现成的 EAM.watch 抓取与对比管线

换掉调制识别的特征集

2–3 天

带宽在固定通带下没有区分度，得换成在 300–3000 Hz 窗口内依然有效的特征：

包络调制谱——语音的音节率集中在 3–8 Hz，数字信号没有； 符号率估计——对包络自相关可以直接读出波特率 （STANAG 4285 = 2400 Bd，4481 = 75 Bd），这比"看带宽猜"精确一个量级； 音调数与间距——FSK 的双音特征在窄带里反而更清楚。 这三个特征加起来，才是真的在识别调制。

前置：缺陷 03（SNR 基准）一并修正

传播条件关联

1 天 · 性价比最高

NOAA SWPC 提供免费 JSON 接口：Kp 地磁指数、F10.7 太阳流量、X 射线耀斑等级。 拉下来存一张表，和信号检测按时间 join。

一次 HTTP 请求 + 一张表的成本，换来的是回答 "11175 为什么在 15 UTC 突然安静了"的能力—— 是没人发报，还是 D 层吸收把它吃了？这是把日志变成仪器的最短路径。

建议顺序

怎么走

  1. 补一个 kiwi_client 帧解析的单元测试，喂进构造好的 SND 帧，断言样本数、seq、S-meter。先让缺陷 01 变成一个红色的测试。
  2. 修帧偏移与 dBm 换算，跑一段新录音，确认 23.4 Hz 谐波消失、S-meter 开始连续抖动。
  3. 会话泄漏 + 通话缝合——两处都很小，做完统计量才开始可信。
  4. 换 SNR 基准（只在 300–3000 Hz 带内算），顺手把调制识别的并列问题一起处理。
  5. 自适应噪声基底静噪，用修好的读数重新标定一次。
  6. 多频率并行 + 同播交叉验证——到这里才值得做，因为它依赖前面每一项。
  7. 之后按兴趣挑：传播关联性价比最高，瀑布图最好看，EAM 结构识别最有意思。
